# 课程产物契约

## 推荐目录

在目标工作区规则允许时采用以下结构；若项目已有文档布局，映射到既有布局，不另造平行体系。

```text
tutorial/
├── index.md
├── glossary.md
├── appendix/
│   └── code-environment.md
├── chapters/
│   ├── 01-<topic>.md
│   └── 02-<topic>.md
└── code/
    ├── <dependency manifests and lockfiles>
    ├── <build, lint, test, and runtime configuration>
    ├── <shared source and verification entry>
    └── demos/
        ├── 01-<topic>/
        │   ├── DEMO.md
        │   └── <source files>
        └── 02-<topic>/
            ├── DEMO.md
            └── <source files>
```

`index.md` 记录学习目标、受众、课程地图、代码环境入口、章节导航和结课验收。`glossary.md` 只收录跨章节反复使用且容易混淆的术语。`code/` 是可直接安装、运行和验证的统一工程。`appendix/code-environment.md` 是独立章节，必须根据最终工程生成。若目标项目已有布局，将这些职责映射到既有路径，不另造平行体系。

## 覆盖矩阵

在开始写章节前维护以下字段，可放在计划中而不必生成独立文件：

| 结课能力 | 核心知识 | 工程实践 | 章节 | 代码环境或 demo | 验收证据 | 权威来源 |
|---|---|---|---|---|---|---|

每项结课能力必须至少关联一个实践和一个客观验收。仅被正文提及不算覆盖。

## 章节契约

每章必须回答：

1. 学完能完成什么可观察任务？
2. 需要哪些已讲授前置知识？
3. 哪些组件参与执行，它们分别负责什么？
4. 最小示例如何形成可运行闭环？
5. demo 如何将概念转为工程操作？
6. 哪些生产因素被保留，哪些被刻意简化？
7. 读者需要完成什么代码修改或故障排查？
8. 哪些权威来源支持关键事实？

## 代码环境配置附录契约

附录必须包含：

- 运行时、SDK、包管理器、框架和主要工具的固定版本及选择依据；
- 完整目录树，以及依赖清单、锁文件和各配置文件的职责；
- 从零安装、启动最小示例、运行格式化检查、静态分析、测试和构建的命令；
- 环境变量、端口、外部服务和凭据的安全配置方式；
- Windows、macOS、Linux 或容器之间实际存在的平台差异；
- 每条验证命令的预期结果；
- 常见安装、版本、端口和依赖错误的定位步骤；
- 教程环境与生产环境之间的明确差异。

附录中的版本、命令、路径和配置必须从最终代码环境读取并实际核对，不得使用计划值或示例值替代。

## Demo 说明书模板

```markdown
# <Demo 名称>

## 目的
<本 demo 验证的单一主要能力>

## 结构
<简短目录树，以及各关键文件的职责>

## 运行
<运行平台、版本、工作目录、安装与执行命令>

## 预期结果
<可观察输出、界面状态、测试结果或制品>

## 执行路径
<用短文或图说明入口、关键调用、数据流和状态变化>

## 教学简化
<省略的安全、性能、兼容性、错误处理或运维因素及其生产替代方案>

## 动手修改
<一个需要学习者自行修改的任务，不直接给完整答案>

## 验收
<命令、断言或检查步骤，以及通过条件>
```

## 完成检查

- 大纲由结课能力反推，章节无关键覆盖缺口。
- 每章由独立子 agent 交付并经主 agent 验收。
- 已生成统一代码环境，锁定依赖，且最小入口可以直接运行。
- 每章有可执行实践和客观验收，不只有讲解。
- 每个 demo 可独立定位运行前提、命令和预期结果。
- 代码说明书简短但涵盖结构、执行路径和教学简化。
- 代码环境配置附录由独立子 agent 根据最终工程生成。
- 附录的版本、目录、配置和命令与实际环境一致。
- 核心事实有高信任来源，版本敏感信息已核实。
- 章节术语、图表、代码、命令和跨章引用一致。
- 从干净环境走通安装、最小示例、检查、测试和最终构建。
