# 创建体系化技术教程

## 确立教学任务

1. 读取目标工作区内适用的 `AGENTS.md`、项目文档和输出约束。若教程基于代码库，再读取其事实入口、依赖清单、锁文件、关键源码、构建配置和 CI 配置。
2. 明确学习者的现实目标、已有基础、目标能力、技术版本、运行平台、时间约束和产物位置。能从请求或工作区确定时直接采用；缺少会实质改变课程结构的信息时再询问。
3. 将目标写成可观察的结课能力，并据此界定范围。不要以 API 清单或“全面介绍”代替课程目标。
4. 优先收集官方文档、标准、源码、论文或公认权威资料。不要依赖未经核实的参数记忆编写版本敏感内容。
5. 区分“来源证实的事实”“参考项目事实”和“作者建议”。为重要结论与版本敏感内容就近提供链接或可定位的代码证据。

## 设计完整课程

先建立“结课能力 → 核心知识 → 工程技能 → 章节 → demo → 验收”的覆盖矩阵。阅读 [course-contract.md](references/course-contract.md)，使用其中的产物契约和检查表。

课程至少覆盖与目标有关的：

- 核心术语、组件职责与运行机制；
- 最小可运行闭环和关键 API；
- 常用组合方式、边界条件与错误处理；
- 项目结构、配置、依赖、测试、调试和可观测性；
- 安全、性能、可靠性、部署或发布等适用的生产实践；
- 常见误区、故障定位和进一步学习方向。

按依赖关系划分章节。每章交付一个明确的工程目标，整套课程覆盖从环境启动、核心实现到测试、调试和交付的完整路径。先说明当前任务需要的概念和约束，再通过可运行代码展示实现方式。

## 生成统一代码环境

在编写正文前，先在教程产物中创建可运行的代码环境。不要只给初始化命令或零散代码片段。

1. 按目标技术选定受支持的运行时、SDK、包管理器、框架和工具版本，并通过官方资料核实兼容关系。
2. 生成完整的项目结构、依赖清单、锁文件、编译或构建配置、格式化与静态检查配置、测试配置、示例环境变量文件和必要的启动脚本。仅添加教程实际使用的工具。
3. 提供一个最小可运行入口和一个自动验证入口，使读者完成安装后能立即看到输出并确认环境正常。
4. 实际执行依赖安装、格式化检查、静态分析、测试、启动或构建命令。修复环境问题后再让章节 agent 基于该环境工作。
5. 固定公共目录、命令、端口、环境变量名称和版本。章节 demo 在同一工程上增量演进；只有技术上必须隔离时才创建独立子项目，并说明原因。
6. 不提交真实密钥、本机绝对路径、全局工具隐式依赖或无法复现的手工步骤。需要凭据时提供安全的占位配置和无凭据替代路径。

把实际环境配置记录为后续“代码环境配置附录”的事实来源。附录必须描述最终环境，不能先写说明再猜测实现。

## 按章节编排子 agent

1. 主 agent 负责课程范围、覆盖矩阵、统一术语、统一代码环境、公共 demo 约定、章节接口、集成和最终验收。
2. 完成全局大纲后，每个章节必须交给一个独立的子 agent；一个子 agent 只负责一个章节，一个章节不得由多个子 agent 分拆撰写。
3. 默认串行调度章节 agent。开始下一章前，主 agent 先验收上一章并固定它为下一章可依赖的前置内容，避免术语、代码和难度漂移。
4. 给章节 agent 提供：读者背景、课程目标、覆盖矩阵、章节契约、已完成章节摘要、已验证的代码环境、允许依赖的公共代码、输出路径、权威资料和验证命令。明确其文件所有权，并提醒不得回退他人的改动。
5. 章节 agent 必须交付章节正文、该章示例或 demo、demo 说明书及验证结果。主 agent 不接受只有正文、代码片段无法运行或没有客观验收标准的章节。
6. 将代码环境配置附录视为独立章节，交给一个独立子 agent 在其他章节和最终环境稳定后编写。
7. 若执行环境不能创建子 agent，暂停章节创作并向用户说明这一硬性约束，不要悄悄改为单 agent 代写。

## 编写章节

每章依次包含：本章目标、前置条件、组件职责与执行路径、逐步讲解、最小示例、教学 demo、demo 代码说明书、工程实践、常见错误、动手任务、验收标准、来源和下一章衔接。

保持语言简洁、准确、具体：

- 一段只解释一个主要观点，先结论后依据；
- 首次出现时定义术语，并始终使用同一名称；
- 精确定义机制、触发条件、作用域和例外；
- 比喻只能辅助精确定义，并说明失效边界；
- 删除不承载信息的开场、重复总结和泛泛鼓励；
- 代码保持最小、完整、可复制，显式标注为教学而省略的生产要素。

选择能降低理解成本的图表：用 Mermaid flowchart 表示流程和依赖，用 sequence diagram 表示交互，用 state diagram 表示状态，用表格表示精确映射，用目录树表示结构。图表必须与正文和代码一致；简单事实不强行画图。

## 创建与说明教学 demo

每章至少提供一个与本章目标直接对应的可执行示例或教学 demo；纯概念章可使用可运行实验、可验证配置或可重复命令替代。所有 demo 必须在统一代码环境中直接运行。优先让相邻章节在同一项目上增量演进，避免多个无关玩具示例。

每个 demo 配套一份精简代码说明书，至少写明：目的、目录与关键文件、运行前提、安装和运行命令、预期结果、关键执行路径、刻意简化项、动手修改和验收方法。说明书解释“为什么这样组织”和“数据或控制如何流动”，不要逐行复述代码。

实际运行适用的格式化、静态分析、测试、启动或构建命令。无法执行时准确记录未验证项、原因和用户可复现的验证命令，不得声称通过。不得在示例中写入真实密钥、令牌或私密配置。

## 集成与验收

所有章节完成后，由主 agent：

1. 合并章节导航、术语表、公共配置和 demo 入口，消除重复与矛盾。
2. 检查章节前置关系、难度曲线、跨章引用和代码演进，确保学习者不会依赖尚未讲授的概念。
3. 用覆盖矩阵确认核心知识点和工程实践都有正文、实践与验收证据。
4. 由独立附录 agent 根据最终代码生成“代码环境配置附录”，说明版本选择、目录结构、依赖用途、配置文件、安装启动、验证命令、平台差异、常见环境问题及排查方法。
5. 从干净环境执行一次“获取代码 → 安装依赖 → 启动最小示例 → 运行检查与测试 → 构建最终 demo”的完整路径。
6. 检查附录、所有图表、命令、文件路径、预期输出、版本和引用与实际产物一致。
7. 最终报告教程结构、代码环境入口、demo 清单、已执行验证、未验证事项及原因。

不要为了显得完整而填充边缘知识。完整意味着目标能力闭环无缺口，而不是篇幅最长。
