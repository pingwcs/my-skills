# 编写代码库教程

## 建立事实边界

1. 读取目标输出仓库及参考代码库中的 `AGENTS.md`，遵守其作用域和文档边界。继续查找更深层的 `AGENTS.md`；更近的规则优先。
2. 确认教程受众、已有经验、目标技术、参考代码库、输出位置和期望深度。能从请求和仓库确定时不要追问。
3. 读取项目指定的事实入口，例如 `README.md`、`CONTEXT.md`、版本清单、锁文件、构建配置、入口文件和 CI 配置。以实际配置和源码为项目事实，不以印象补全。
4. 将信息标记为三类：代码库已证实、官方资料已验证、作者建议。不要把建议写成项目现状。
5. 若输出仓库的规则与用户要求冲突，说明冲突并请求决策；不要擅自越过文档边界。

## 提取课程范围

先建立“源码证据 → 知识点 → 课程”的映射。使用搜索定位依赖、导入、入口、状态流、网络层、持久化、平台集成、构建脚本及发布配置，并打开关键实现核实上下文。不要仅凭文件名或依赖名推断用法。

至少区分以下层次：

| 层次 | 回答的问题 | 常见证据 |
|---|---|---|
| 语言 | 代码如何表达类型、控制流与异步逻辑？ | 源文件、语言配置 |
| 框架 | UI、生命周期、状态与组件如何组织？ | 入口、组件树、框架依赖 |
| 工具链 | 如何解析依赖、生成代码、分析、测试和打包？ | 清单、锁文件、脚本、CI |
| 运行时 | 代码在哪里执行，生命周期和平台边界是什么？ | 平台目录、插件、运行配置 |
| 生产构建 | 如何得到可发布制品，签名、环境和优化如何处理？ | release 配置、构建命令、CI |

只讲与学习目标相关的基础知识，以及理解参考项目必需的实际知识点。为每个项目专有结论记录可定位的文件证据。

## 设计渐进式课程

按依赖关系安排课程，而不是按 API 名录堆砌：

```mermaid
flowchart LR
  A[环境与工具链] --> B[语言核心]
  B --> C[框架心智模型]
  C --> D[最小可运行示例]
  D --> E[参考项目架构]
  E --> F[调试与测试]
  F --> G[生产构建与发布]
```

每课包含：学习目标、前置知识、核心模型、最小示例、参考项目证据、可执行步骤、常见误区、练习、验收标准。先解释模型，再展示语法；先给最小闭环，再进入项目级组合。

优先使用适合关系的图表：流程用 Mermaid 流程图，时序用 sequence diagram，状态变化用 state diagram，分层与映射用表格，目录结构用树。单一事实或简单步骤直接写短句，避免为了图表而图表。

## 保证语言严谨

- 使用准确中文和 canonical English 技术术语；首次出现时采用“中文名称（English term）”，之后保持一种写法。
- 明确区分编译期与运行时、开发构建与生产构建、SDK 与框架、包管理器与构建系统、模拟器与真实设备。
- 比喻只能辅助已给出的精确定义，并明确比喻的适用边界；不要用比喻替代机制说明。
- 避免“自动”“底层”“原生”“性能更好”等无条件断言。写出触发条件、作用域和例外。
- 示例保持最小、完整、可复制；解释省略的生产要素。

## 验证版本敏感内容

1. 从锁文件、版本管理配置和命令输出确定实际版本。
2. 对安装步骤、CLI 参数、平台要求、构建与签名流程查询对应版本的官方文档或工具帮助。技术资料优先使用官方文档和项目自身配置。
3. 在安全且可行时实际运行环境诊断、依赖安装、静态分析、测试、启动或构建命令。生产构建可能需要密钥、账号或平台环境时，验证到可达边界并明确阻塞项。
4. 不可执行时写明“未执行”及原因，不得声称验证通过。不要伪造终端输出、制品路径或项目能力。
5. 命令注明工作目录、shell 和平台前提；路径或参数需要替换时使用显眼占位符。

生产章节至少说明：环境配置来源、依赖锁定、优化或混淆的实际状态、签名与凭据边界、构建命令、制品位置、发布前检查。不要把命令中的 `release` 或类似名称误写为已满足全部生产要求。

## 编写与验收

在允许的文档位置直接编写教程，并维护既有导航或索引。除非用户明确要求，不创建规则之外的辅助文档。

完成前逐项检查：

- 每个项目事实能追溯到源码或配置。
- 所有版本敏感命令已按当前版本核实，并标明验证程度。
- 语言、框架、工具链、运行时和生产构建没有混为一谈。
- 图表与正文一致，代码块可独立复制，命令包含执行上下文。
- 课程从基础到项目实践递进，每课均有练习和客观验收标准。
- 术语前后一致；比喻之后仍有精确定义和边界。
- 未泄露密钥、令牌、签名材料或本地私密配置。

最终报告输出文件、覆盖范围、实际执行的验证、未验证事项及原因。
